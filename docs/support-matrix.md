# Support matrix — Task 1

**Report-assisted, human-declared** (see `docs/evals/evaluation-methodology.md`):
the latest `full`-suite eval report suggests a status; a human declares the
final status with a reason; README and the frontend render this same data.
A pass-rate does not threshold itself into "supported" — declaring is an
engineering-judgment act, and the reason column is the graded honesty evidence.

Entry shape (also served as JSON to the frontend):

```json
{
  "domain": "wikipedia.org",
  "task_type": "TC2 search-then-extract",
  "eval": "7/8",
  "declared_status": "unreliable",
  "reason": "Disambiguation pages still misroute the extraction step (case tc2-wiki-004)."
}
```

## Declared limitations (M6 live breadth)

| Limitation | Evidence | Status |
|---|---|---|
| Live TC1 on news.ycombinator.com and openlibrary.org is stub-verified only (still true, and now the *only* live qualification) | `live-hn-item1-title` and `live-ol-edition-title` pass with hand-written plans; the live planner has never been run against either domain | `unreliable` — the same stub-vs-planner asymmetry declared for books.toscrape.com. The resolver/executor/verifier path handles both real DOMs; planning quality on them is unmeasured until a `full` run |
| **Closed 2026-08-18** — openlibrary.org was unreachable for the last day of M6, and half of what looked like the outage was ours | the host recovered; `live-ol-search-a11y-invisible` went green on the first attempt (its first green ever), and `live-ol-edition-title` kept failing `nav` until the wait condition was fixed — the page loads in 4.4s under `domcontentloaded` with the expected heading present, and times out at 25s under `load` (ADR-007) | `supported` — the live suite is 6/6 and all three live domains now rest on runs against current code. Kept as a row rather than deleted: the declaration was correct on its date, and the lesson is that a case declared unreachable should be re-run rather than allowed to harden into a conclusion |
| **Closed 2026-08-18** — a page whose `load` event never fires is unreadable, though its content is complete | `nav-load-event-never-fires` (pre-plan hop) and `nav-action-load-event-never-fires` (the `navigate` step), both watched red; the second re-watched red *after* the first was fixed, since `run_task` has two `page.goto` calls and fixing one would have left the other green-but-broken | `supported` — both route through one `navigate()` helper: `domcontentloaded`, then a **bounded** 2s wait for `load`, swallowed on timeout. A healthy page pays nothing; a hanging one is read instead of blamed. `networkidle` was tried first and rejected on measurement: +34s on the fast suite, over the ADR-002 budget (ADR-007) |
| An observe case pointed at an incompatible fixture reads as a broken observer, not a bad subject | no case — `_run_observe_case` on `slow-asset.html` raises `TimeoutError` after 30.4s (measured in the #9 review). Marked `ponytail:` at the call site | `unreliable`, eval-harness only — **declared, not fixed**. The strict `load` wait is correct there and stays: production asks "is this page usable enough to act on?", observe ground truth asks "what does a fully settled page expose?", and collapsing the two would leak the production contract into the harness. What is wrong is the *budget*: it inherits Playwright's 30s default rather than one anyone chose, and a timeout surfaces as a traceback instead of a result. Upgrade path: keep strict `load`, give it an explicit 5–10s eval budget, and return a structured `eval_env` failure. No production path touches it and no existing case reaches it |
| **Closed 2026-08-18** — a best-effort screenshot could block a run for 30s per step | same two cases: 32s and 64s before the bound, 4.3s and 8.4s after | `supported` — `page.screenshot()` waits for fonts, which on a page whose `load` never fires runs to its 30s default, inside a `try/except` whose comment says failing there is acceptable. Best-effort and unbounded cannot both be true; it gets the same 2s budget as a postcondition. No case asserts it — it is a latency property and there is no timing-assertion mechanism here — so the evidence is the committed report, named in ADR-007 rather than implied |
| A control invisible to both the a11y tree and the light DOM cannot be located | `live-ol-search-a11y-invisible`: Open Library's homepage search field exposes zero searchbox/combobox/textbox roles and no visible `<input>` — it is mounted by JS behind a reveal interaction (hand probe, 2026-08-17) | `unsupported` — no locator tier in the contract can reach it, a hostility class no fixture represents. The **diagnosis** is now proven live: after two runs that failed for other reasons (`failure:act` before the M6 fix, `failure:nav` during the outage), the case went green on 2026-08-18 — `failure:locate`, diagnosis 1/1, on a real site nobody here authored. The control remains unreachable; what is supported is saying so correctly instead of fabricating |
| **Closed at M6** — relocation onto a non-actionable element launders the failure class | was: report 20260817-024235-live, diagnosis 0/1 — the unresolvable searchbox relocated to a text-tier match on the literal string "Search" and the `Locator.fill` error reported `failure:act` for a root cause of `locate`. Now: `relocate-fill-non-editable` (fixture twin, watched red at `failure:act`) | `supported` — the guard sits in the executor's fill path, not in the relocate rung, so a first-attempt plan that targets a non-fillable element is classified the same way. An element that cannot hold a value is the wrong element, which is `locate`; a readonly or disabled input is the right element in the wrong state and stays `act` |
| **Closed at M6** — unknown target-schema keys are silently dropped by the resolver | was: `live-hn-item1-submitter`'s `near:` resolving as bare `{role: link}` → `ResolveError: 39 matches`, ignored rather than rejected. Now: `resolver-unknown-target-key` | `supported` — the five keys in `specs/001-browser-contract.md` are the whole schema and anything else stops the run as `failure:task`, naming the key |
| **Closed at M6** — `near:` was advertised in the contract and never implemented | `live-hn-item1-submitter` (39 links, the submitter picked by proximity to "points by"), `live-books-detail-upc` (a spec-table value picked by its label), `tc1-shop-price-near`, `near-excludes-its-own-anchor` | `supported` — document-order proximity, with the anchor's own element excluded and the refusal rules in the row below. It is the first mechanism to emit the `structural` tier in any run. Not a relocation rung: the ladder still climbs between `role` and `text` only |
| **Closed at M6, after a cold review** — `near:` returned confident wrong answers on three page shapes `shop.html` does not have | `near-anchor-substring` (anchor "Total" bound to "Subtotal" → the subtotal returned as the order total), `near-prefers-the-container` ("which row costs $24.50" → a different product at a different price), `near-equidistant-is-ambiguous` ("which product costs $24.50" → "Add to cart") | `supported` — anchors match exactly before loosely and keep only the deepest match; a candidate wrapping the anchor outranks every neighbour; and both kinds of ambiguity (two disjoint anchor matches, two equidistant candidates) are loud `locate` failures instead of tie-breaks. All three had reported `success` with a `PASS` verdict and nothing in the trace to suggest doubt |
| **Closed at M6** — a relocation rung dropped the `near` constraint it was recovering | `relocation-preserves-near`: a failed `{role, text, near}` relocated to `{role, name}` with proximity deleted, resolved a different element and reported success | `supported` — rungs carry `index` and `near` forward as intent. Found by the M6 spec-drift audit, not by the suite: `resolver-unknown-target-key` surviving one layer down |
| `near:` degenerates to first-candidate inside shadow DOM | no case — no fixture in the repo uses shadow DOM (M6 cold review) | `unsupported`, declared: Playwright's locators pierce open shadow roots and `document.querySelectorAll('*')` does not, so an anchor or candidate inside one scores `indexOf === -1`, every candidate ties, and the first wins — reported as `structural`, `success`. Not fixed because a fix with no fixture behind it is how the three defects above shipped |
| A fill into a contenteditable field is failed `act` after it worked | no case — no fixture has a contenteditable (M6 cold review) | `unreliable`, in the safe direction: `FILLABLE_JS` admits `isContentEditable`, then the readback calls `input_value()`, which throws on anything that is not a form control. Every modern rich-text composer is this shape |
| **Closed at M6** — a correct answer can be graded FAIL because the stored evidence is narrower than the page | `evidence-window-keeps-the-anchor`, found by `live-books-detail-upc`: right value, anchor present on the page, runtime check passed, eval verdict FAIL — the identity anchor was 2000+ characters from the value on a product page with a long description | `supported` — the evidence window now keeps a slice around the anchor as well as the value. A false FAIL is the safe direction and still a defect: in a report it is indistinguishable from a run that really did read the answer off the wrong entity's page, and M7 computes verifier precision from exactly these verdicts |

## Declared limitations (M5)

| Limitation | Evidence | Status |
|---|---|---|
| Live TC3 on books.toscrape.com is `unreliable`, not `supported` | `live-books-travel-price` passes with a **stubbed** plan; the same task with the **real** planner failed on the deployment (run `cd7121fc`) | `unreliable` — the two results disagree, and the disagreement is the finding. With a hand-written plan the resolver/executor/verifier path handles the live DOM; with the live planner the run failed loudly at `failure:locate`. Declaring this `supported` on the strength of the stubbed case would be exactly the flattery this table exists to prevent |
| The live planner emits target roles that are not ARIA roles | deployed run `cd7121fc`: `{"role": "text", "name": null, "text": null}` → `ResolveError: no tier resolved` → `failure:locate` | `unreliable` — the planner reaches for a `text` "role" when it wants to read text. The agent fails loudly with the right class and no fabricated answer, and relocation correctly finds nothing to climb to (a target with neither name nor text has no rungs), so the cost is a failed run rather than a wrong one |
| Live extraction from a table is positional | `live-books-travel-price` targets `{role: cell, index: 5}` | `unreliable`, and **superseded at M6**: ARIA makes `rowheader` a subclass of `cell`, so label and value cells interleave and the price is reached by counting. The semantic form, `near:`, was advertised in the `specs/001-browser-contract.md` target schema and never implemented — the spec-drift declared at the freeze. It is implemented now and `live-books-detail-upc` reaches a table value by naming its label. This row stays because the *old* case still counts: a plan may still target a cell positionally, and nothing forces the semantic form |
| "The deployed URL was verified" has a shelf life, and the claim rarely carries one | deploy-smoke runs on push and on a 02:17 UTC cron. On 2026-08-18 the deployment served the M6 build and passed deploy-smoke at 14:02 UTC (run `32037391876`), then returned 404 on every path — edge with nothing bound behind it — by 18:04, with no push in between. The build was fine; the platform stopped serving it | `unreliable` — an outage starting between pushes is invisible for up to 24h, and today's cron will catch this one hours after it mattered. Not an argument for more polling: an argument that every claim about the deployed URL should carry the timestamp it was true at, which is why the run ids in this table do |
| The paid submit endpoint has no per-IP rate limit | M5 operator error: a polling loop submitted ~30 runs before anyone noticed; see `docs/analysis.md` §8a | `unsupported` by omission — per-IP limiting is backlog. Spend is bounded per *run* (30 actions, 100k tokens) but not per *caller*, so a careless loop (or an unfriendly one) can spend repeatedly. The concurrency semaphore serialises the damage but does not cap it |
| A redeploy destroys the run history | same incident: the runs that mattered most were unrecoverable because the process restarted | `unsupported` by design — `RUNS`/`STREAMS` are in-memory (analysis §4). Acceptable for a reviewer demo, and the reason the cost of that incident can only be given as an upper bound |
| Capability is about one hop deep | T9 held-out probe: 2 correct answers in 8 answer-seeking tasks. Second hops, aggregates and comparisons all failed. **Confirmed on the deployed M6 build**, run `734d3d1f` (2026-08-18): "find the cheapest book and tell me its exact price" was planned as `extract {"role": "article", "index": 0}` and returned the FIRST product, £45.17 instead of £23.21 — `success`, `PASS` | `unreliable` — the two successes were single-hop extractions whose answer string was already in the pre-plan observation. There is no compare/rank/filter step in the plan vocabulary, so "which is cheapest" is planned as "extract the whole list" |
| Values that exist only in an HTML attribute cannot be read | T9 probe #1 and #6: listing titles are CSS-truncated to `A Light in the ...`, with the full string only in `title=`/`alt=` | `unsupported` — extraction reads element text, so the run fails loudly (`failure:semantic` on the identity anchor, or an empty extraction) rather than returning the truncated string |
| With no start URL, the planner plans blind | T9 probe #7: step 1 came back `note: null`, `postcondition_ok: null` — no observation happened; the plan emitted `{"role": "article"}` and failed `locate` | `unreliable` — commit `ed1f774` ("the planner never plans blind") covers only the URL-supplied path, where there is a page to observe. Spec drift found by the probe, declared rather than fixed at the freeze |
| The keyword scope screen over-refuses on non-instrumental phrasing | `l5-refuse-login-contracted` (the row deliberately removed from it): "What is the sign in the shop window?" is refused | `unreliable`, in the safe direction — the words in "sign in the shop window" and "sign in to my account" are identical and only intent differs, which no keyword screen can separate. First eval evidence that the deferred LLM screening has a real job |
| An answer is never checked for being *responsive* to the question | T9 probe #5: a 20-book page dump was returned as the answer and rejected only by `grounded`, on a whitespace mismatch. Deployed run `734d3d1f` is the sharper case: the answer was a whole product tile, grounded and anchored, responsive to "which product" but not to "which is cheapest" | `unreliable` — the verifier checks that an answer is grounded, anchored and matches ground truth where available, but nothing asks whether it addresses the task. In that run the no-fabrication guarantee held by luck |
| Planning quality unmeasured | every `fast` case stubs the planner at the module boundary | by design (cost-discipline); the `full` suite is the only measurement |
| Values in ARIA name-prohibited elements (`<dd>`, `<dt>`, `code`, `time`…) cannot be targeted **by role+name** | `observe-name-prohibited-roles`; the M6 counter-example is `near-excludes-its-own-anchor`, whose target `{role: cell, near: "UPC"}` carries no name at all | `unreliable`, corrected at M6 (was `unsupported`): the observation still blanks the unusable name, so role+name still cannot reach them and the agent still fails loudly rather than planning an unresolvable target. But `near:` reaches them by role + proximity, which is what a `<dt>`/`<dd>` pair is for. The limitation is narrower than it was declared |
| A locator broken at **both** reachable tiers is not recovered | `l4-shop-button-text-renamed` recovers text → role+name, `l4-recover-name-to-text` the reverse | `unreliable` — relocation has exactly two rungs to climb between: `role` and `text`. M6 made `structural` reachable (`near:`), but only when a *plan* asks for it — it is not a relocation rung, because a rung must be derivable from the failed target's own strings and a proximity anchor is a different element's text. So a mutation that kills both reachable tiers still has nowhere to go. `attrs` exists in the taxonomy and in no code path |
| An identity anchor can be satisfied by evidence from a discarded attempt | `verifier-superseded-not-a-loophole` pins the trace half only | `unreliable` — supersede hides a failed attempt from trace grading, but `evidence_text` is still built from every extraction, including the superseded one (ADR-005) |
| A replan is refused when the failed action changed nothing on the page | `replan-cannot-launder-noop-action` vs its benign twin `recovery-replan-postcondition` | `supported`, with a ceiling: the test is whole-body text equality, so an action whose only effect is visual or off-page reads as no change and its recovery is refused — loud, and in the safe direction |
| Relocation rung 1 ignores the target's role, and a rung is never guaranteed to be a different *element* | no case yet; found by cold review (ADR-005), sharpened by the M6 cold review | `unreliable` — a target `{role: link, text: X}` can relocate onto a same-named heading, a common listing-page shape. The M6 half: a failed `{text: "Search"}` relocates to `{role: button, name: "Search"}` — provably the same button — and still counts in `recovery_rungs`. It cannot create a false green, but every "N rungs tried" figure published here is an upper bound, not a count of distinct attempts |
| The progress stream is graded on the executor's hook, not on the SSE endpoint | `stream-shows-every-step` installs its own `on_step` and compares step ids only | `unreliable` — the gateway's own emitter and its copy semantics are untested, and a stream that stripped step *contents* would still pass (ADR-005) |
| Recovery is reported as a floor, not a rate | 3 injected cases assert recovery; 6 rungs were tried to produce them | by design (ADR-003) — three cases is not a population. It stays `x/y` with the denominator printed until a live suite gives it one |
| Near-miss entity whose name contains the target's name | `trap-near-miss-entity` | caught only with external ground truth; a live run's runtime anchor passes it |
| Identity anchors on aggregate pages (listings, search results) | `trap-search-not-executed`, and now a live instance: deployed run `734d3d1f` anchored on `"Travel"` — the category, which every product on the listing satisfies — and the wrong product passed the check | `unreliable` — every candidate entity is in the page text, so the anchor certifies the wrong answer too. The larger of the two anchor holes, and it sits exactly where TC2/TC4 live. |
| The `fast` suite never runs observe → plan → resolve | all fixture cases inject a stub plan at the planner boundary | by design (cost-discipline), but it means the L4 self-maintenance passes are measured on plans hand-authored against the mutated DOM. Only the `full` suite closes this. |
| A click whose effect cannot be asserted | `postcondition-unverified-click` | `unsupported` by choice: the run fails loudly rather than reporting an unverified state change as success |
