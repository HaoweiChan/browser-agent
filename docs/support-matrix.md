# Support matrix — Task 1

**Report-assisted, human-declared** (see `docs/evals/evaluation-methodology.md`):
the latest `full`-suite eval report suggests a status; a human declares the
final status with a reason; README and the frontend render this same data.
A pass-rate does not threshold itself into "supported" — declaring is an
engineering-judgment act, and the reason column is the graded honesty evidence.

Entry shape (also served as JSON to the frontend):

```json
{
  "domain": "wikipedia.org",
  "task_type": "TC2 search-then-extract",
  "eval": "7/8",
  "declared_status": "unreliable",
  "reason": "Disambiguation pages still misroute the extraction step (case tc2-wiki-004)."
}
```

## Declared limitations (M7 verifier accuracy)

| Limitation | Evidence | Status |
|---|---|---|
| **D1** — `not_a_dump` closes only the single-extraction dump shape; chunking the same dump across several extractions evades it entirely | record id *chunked-dump-cheapest* in `evals/labels/verifier-sample.jsonl`: same task and fixture as record *probe5-shop-listing-dump* ("which product is the cheapest, and what is its price?" on `shop.html`), but the plan chunks the sorted catalogue into four separate `{role: listitem, index: 0..3}` extractions instead of one whole-container extraction. Each extraction's own ratio is ~12%, far under `DUMP_RATIO=0.35`, so all four pass and the runtime verifier returns PASS on a page dump | `unreliable` — this is the largest bound on M7's gain. `verify()` never receives the task text, so no L1 check, present or plausible, can tell "list every product" from "which is cheapest" given structurally identical per-extraction evidence; closing it needs the task text at the `verify()` call site (a contract change: the verifier takes raw evidence only, by design) or ground-truth L2, absent at runtime (`specs/decisions/ADR-008-m7-verifier-accuracy.md` Decision 5) |
| **D2** — `not_a_dump`'s threshold is chrome-sensitive and thinly calibrated | the ratio is computed against the size of the real page the value was read from (`body_len`, since the M7.1 fix — case `verifier-dump-ratio-anchor-flip`; see D4 below for what it was computed against before), so the same dump on a page with more surrounding boilerplate (sidebar, breadcrumbs, pagination, footer) dilutes toward and under 0.35. Calibrated on exactly two positive examples, at ratios 0.4541 and 0.5231 — only ~0.10 of headroom above the 0.35 threshold (`specs/decisions/ADR-008-m7-verifier-accuracy.md` Decision 2); both are unsaturated (their evidence window is the whole real page, not a truncation of it), so the fix does not move either number | `unreliable`, declared — no fixture in the repo carries enough surrounding chrome to demonstrate the dilution, and a two-point calibration sample is thin; a heavier-chrome fixture would sharpen or move the threshold |
| **D3, closed 2026-08-19** — a correct answer can false-FAIL `not_a_dump` on a sparse page | was declared rather than guarded, on the grounds that no fixture in the repo was sparse enough to demonstrate it. Falsified inside the same PR that declared it: main added `src/browser/fixtures/slow-asset.html` (37 clean chars of body text) for its own navigation cases, and its correct answer — the page's `<h1>`, 23 clean chars — is 62% of the page. `not_a_dump` FAILed it, taking `nav-load-event-never-fires` and `nav-action-load-event-never-fires` (main's cases, same extraction) down with it, alongside a case written for exactly this shape, `verifier-sparse-page-not-a-dump`. All three watched red on the merged tree: `checks.not_a_dump: false` | `supported` — `MIN_PAGE_CHARS = 100` (`verifier.py`) restores the floor `MIN_EVIDENCE` used to guard (removed at M7, ADR-008 Decision 3, for lack of exactly this evidence) below which `not_a_dump` does not apply at all. 100 sits between the sparse fixture (37/39 chars) and the smallest confirmed real dump, record *probe5-shop-listing-dump* (195 chars) — every extraction the `fast` suite produces below 100 chars was checked directly, and only the sparse fixture has a ratio anywhere near `DUMP_RATIO` (next highest 0.17); no confirmed dump is smaller than 195 (`specs/decisions/ADR-008-m7-verifier-accuracy.md` Decision 7). Kept as a row rather than deleted — the declaration was correct on its date, and the lesson is the same as the M6 `near:` rows below: a "no case demonstrates this" limitation is a claim about the eval set's current coverage, not a proof the shape cannot occur |
| **D4** — on a page longer than `PAGE_TEXT_KEEP`, a record with no `body_len` reads `not_a_dump`'s denominator from the *stored evidence window* instead of the real page — the window is capped at `PAGE_TEXT_KEEP` and doubles when a distant identity anchor forces a second window onto it, so the ratio stops scaling with the real page: a value over ~700 clean characters reads as "a dump" regardless of true page size, and the SAME value on the SAME page can flip PASS/FAIL depending only on whether the plan happened to carry a distant anchor (case `verifier-dump-ratio-anchor-flip`, red before the M7.1 fix: a 776-char value on a 4,388-char page — window 2000, ratio 0.388, FAIL; the identical value/page with a distant anchor — window 3615, ratio 0.2147, PASS) | closed going forward: `agent.py` now records `body_len` (the real page length) on every extraction, and `verify()` prefers it. Still open for the frozen M7 hand-labeled sample (`evals/labels/verifier-sample.jsonl`), which predates the field and always takes the fallback: **6 of its 28 extractions have a saturated window (window length ≥ `PAGE_TEXT_KEEP`, max 3,560 characters)**, so those six ratios are judged against a truncated-or-doubled window rather than their page. None of the six cross `DUMP_RATIO` either way (all far under 0.35), so the pinned confusion matrix in `evals/adversarial/verifier-precision-recall.json` is unaffected — but that is this sample's luck, not a property of the fallback | `unreliable`, permanently — the fallback exists because the 25 frozen records must keep replaying byte-for-byte (`specs/decisions/ADR-008-m7-verifier-accuracy.md`), so this shape cannot be closed for them without re-capturing (and re-hand-labeling) the sample |
| Ten focused, wrong answers pass the runtime verifier untouched | `verifier-precision-recall`'s 10 pre-existing false positives: wrong field, wrong table row, unsorted "cheapest", a search filled but never executed, a form filled but never submitted, a near-miss "Pro" variant — 4 of the 10 on live sites (`evals/labels/verifier-sample.jsonl`) | `unreliable` — none of these are page dumps, so `not_a_dump` was never going to reach them; closing this needs ground truth (L2, absent at runtime) or an evidence-only LLM check (L3, absent by design) |
